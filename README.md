# Robot WebRTC

This repository contains the signaling website for the Raspberry Pi robot and
a reproducible production stack for the site, HTTPS, and Coturn. The browser
opens a WebRTC connection to the robot; Coturn relays video and control traffic
when the two peers cannot connect directly.

## Production architecture

```text
Browser -- HTTPS/WSS --> Caddy --> Go signaling site
    |                                  |
    +-------- TURN UDP/TCP ------------+
                    |
                 Coturn <-------- WebRTC robot client
```

The stack exposes:

- `80/tcp` and `443/tcp,udp` for Caddy (HTTPS, WebSockets, and HTTP/3)
- `3478/tcp,udp` for TURN
- `49160-49200/udp` for TURN relay traffic

The 41-port relay range is intentionally small. It supports roughly 20
simultaneous relayed peer connections; increase the range if this site will
serve more concurrent viewers.

## Server prerequisites

- A Linux server with a public IPv4 address and Docker Engine with Compose
- DNS records for the site and TURN names pointing to the server
- The ports listed above allowed by both the cloud firewall and the host
  firewall; if the server is behind NAT, forward them to the server

Create the deployment configuration:

```sh
cp .env.example .env
mkdir -p secrets
openssl rand -hex 32 > secrets/turn_shared_secret
chmod 600 secrets/turn_shared_secret
```

Edit `.env` with the real hostnames and public IPv4 address. `SITE_HOST` is the
website name (for example `noremac.dev`); `TURN_HOST` is a DNS name such as
`turn.noremac.dev`. Both may resolve to the same server. The secret file is
mounted into both the site and Coturn and is excluded from Git.

Start and verify the stack:

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app caddy turn
curl --fail https://YOUR_SITE_HOST/healthz
```

Caddy obtains and renews the site's TLS certificate automatically. Coturn uses
time-limited HMAC credentials generated by `/turn-credentials`; the shared
secret is never returned to the browser. The current stack offers TURN over
UDP and TCP on port 3478. If clients must work on networks that permit only TLS
on port 443, run TURN/TLS on a separate public IP because Caddy already owns
443 on this host.

To deploy an update:

```sh
git pull --ff-only
docker compose up -d --build
```

Docker volumes retain Caddy certificates across container replacement. Back up
the repository's `.env` and `secrets/turn_shared_secret` somewhere encrypted;
everything else in this server stack can be recreated from Git.

## Two robot protocols

`cmd/client` uses the newer outbound WebSocket/JPEG protocol at `/ws/robot`.
`cmd/webrtc-client` is the restored Pion client for `/ws/webrtc`; it uses
Coturn and streams H264 over WebRTC. They are intentionally separate binaries
and are not interchangeable.

## Local development and verification

Run the site locally with a development TURN secret:

```sh
TURN_SHARED_SECRET=development-only TURN_HOST=localhost go run .
```

Open `http://localhost:8080/robot/`. Run all automated tests with:

```sh
go test ./...
```

## WebRTC client for OrcasMakers

The restored Pion implementation is a separate executable, so it cannot be
confused with the default JPEG/WebSocket client:

```sh
go run ./cmd/servo
ROBOT_WEBRTC_TOKEN=replace-me go run ./cmd/webrtc-client
```

It connects to `wss://orcasmaker.com/ws/webrtc`, fetches temporary credentials
from `/webrtc/turn-credentials`, publishes H264 camera RTP, and receives the
same controls through a WebRTC DataChannel. Override the endpoint with
`ROBOT_WEBRTC_SIGNAL_URL` or `-signal-url`. The token must match
`/etc/orcasmakers/robot-webrtc-token` on the OrcasMakers server.

GitHub Actions builds `robot-client` and `robot-webrtc-client` as distinct ARM64
artifacts. Configure `ROBOT_SITE_URL` and `ROBOT_WEBRTC_SIGNAL_URL`; the robot
bearer token remains a runtime secret and is not compiled into either binary.
